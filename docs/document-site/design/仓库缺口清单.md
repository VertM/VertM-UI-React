## P0 — 影响发布与安装

### 1. `@vertm/react` 未把 `@vertm/styles` 声明为依赖 ⬇️ **2026-10-10 降为 P1**

> 降级理由：即使加进 `dependencies`，用户仍要手动
> `import '@vertm/styles/index.css'` 才有样式，加依赖只省掉一次 `npm install`，
> 解决不了"忘记引 CSS"。快速上手页（`getting-started.md` 第 11、20 行）
> 已写明安装与引入步骤，FAQ 也有排查提示，不阻塞发布。
> 以下为原始分析，保留备查。

**证据**：`packages/react/package.json` 的 `dependencies` 仅含
`@vertm/core`、`@vertm/icons`、`@vertm/tokens`，**无 `@vertm/styles`**。

**影响**：README 让用户装三个包，掩盖了问题。真实用户若只装
`@vertm/react`，组件将**完全没有样式**——`writing-mode: vertical-lr`
来自 `@vertm/styles/src/vertical.css`，缺失时页面渲染为横排且布局塌陷。
这类 issue 标题通常是"装完没样式"，很难自查。

**建议**：把 `@vertm/styles` 加入 `dependencies`。理由是
`VertMConfigProvider` 本身就依赖 `vertical.css` 的原子类，不是可选增强。

### 2. `@vertm/wasm` 的 `.wasm` 产物 ~~需验证~~ ❌ **本条作废，判断有误**

**原判断**：以为 `tsc` 不复制 `.wasm` 二进制，导致产物缺失。

**实际情况（2026-10-10 核实）**：这个包**根本不打包 `.wasm`**。
`packages/wasm/src/index.ts` 只有 102 行，通过
`await import('harfbuzzjs')` 动态加载——即 `.wasm` 由 **`harfbuzzjs` 这个
peer 包**在运行时提供，`@vertm/wasm` 自己只发TypeScript 编译出的胶水层。

`dist/` 内容与 `files: ["dist"]` 完全匹配，无遗漏。

**但这暴露了另一个真实问题**（见下条2b）。

### 2b. ~~`@vertm/wasm` 未声明 `harfbuzzjs` 依赖~~ ✅ **本条作废，判断有误**

**原判断**：以为 `harfbuzzjs` 既不在 `dependencies` 也不在
`peerDependencies`，只在错误信息里让用户手动装，属于灰色地带。

**实际情况（2026-10-10 复核）**：`packages/wasm/package.json` 里有

```json
"optionalDependencies": { "harfbuzzjs": "^0.4.4" }
```

**这是完全正确的做法**——我此前 grep 时只查了 `dependencies` 与
`peerDependencies` 两个字段，漏了 `optionalDependencies`，导致误判。

装 `@vertm/wasm` 时会顺带安装 `harfbuzzjs`；若用户用 `--no-optional` 跳过，
`shapeMongolianText()` 抛出带安装指引的错误，其余功能不受影响。
**无需改动。**

### 3. 版本号已推进至 0.2.0，但跨包版本不齐 ⚠️ 部分作废

**原判断**：六个包全部 `0.1.0`。

**实际情况（2026-10-10 核实）**：`core` / `icons` / `react` 已发到 **`0.2.0`**
（commit `d6e149e chore: release 0.2.0 for core, icons, and react`），
但 `styles` / `tokens` / `wasm` 仍在 `0.1.0`。

**仍存在的问题**：`@vertm/react@0.2.0` 依赖
`@vertm/core@^0.2.0`、`@vertm/icons@^0.2.0`，但 `@vertm/tokens` 仍是 `^0.1.0`。
跨包版本不齐本身不是错（tokens 稳定在 0.1.x 是合理的），但**发布时需在
CHANGELOG 说明哪些包变了、哪些没变**，否则用户升级 `react` 后会困惑于
「为什么我只升了一个包」。

`CHANGELOG.md` 目前以提交记录为主，缺面向使用者的迁移提示——这条仍然成立。

**建议**：token 字段仍在变（`tokens` 停在 0.1.x），破坏性变更必须升 minor。
CHANGELOG 增加 Breaking Changes 段落，并标注跨包版本差异。

## P1 — 影响可信度与使用体验

### 4. 组件文档缺「键盘」小节 ✅仍存在

**证据**：`docs/component-design-spec.md` 定义了方向契约
（ArrowUp/Down 走上下文字，ArrowLeft/Right 走列/层级）；
`Menu.tsx` 有 `EditorialKeyboard.test.tsx`；0.2.0 起键盘契约已下沉到
`packages/core/src/interaction/keymap.ts`。
组件页由 dumi `atomDirs` 从 `packages/react/src/*/index.md`（及 `packages/icons/src/icon.md`）
生成，共 46 页，**其中 0 页有 `## 键盘` 小节**。
（原文写的 `packages/docs/docs/components/*.md` 路径不存在，也不要在那里新建文件，会与生成的路由冲突。）

**影响**：竖排组件库的键盘行为与横排直觉相反（Select 上下移动、竖排时右键确认；
Menu 上下同级、右进子菜单、左回退；Tabs 竖排时始终左右切换；
单行 Input 用上下键移动光标）。
这是**最难靠用户自己发现**的信息，藏在代码和测试里等于不存在。
迁移过来的用户会先撞上这堵墙。

**建议**：每页加固定「键盘」小节，放在「竖排提示」之后、「API」之前
（现有页面模板是示例在前，不打乱）。内容以 `keymap.ts` 为准，
对照 `docs/component-design-spec.md` §3.1 的方向契约。逐页清单见
`handoff/组件文档页清单.md`。

### 5. ~~`packages/icons` 无文档入口~~ ❌ **本条作废，判断有误**

**实际情况（2026-10-10 核实）**：`.dumirc.ts` 的 `atomDirs` 包含
`{ type: 'component', dir: '../icons/src' }`，`packages/icons/src/icon.md`
已生成 `/components/icon` 页，总览页的 Icon 瓦片也指向它。
原判断只查了 `packages/docs/docs/`，漏了 atomDirs。

**可选增强**：在现有 Icon 页里补一张图标总览，标注每个图标在竖排下的旋转方向。

### 6. 站点控制菜单未接入引导 🆕 本次新增

**证据**：`SiteControls.tsx` 实现了 9 主题 + 2 书写模式切换，
但 `docs/index.md` 的 CTA 只有「开始使用」「浏览组件」，
**未引导用户发现顶栏的主题切换**。

**影响**：这是全站最有交互价值的功能（实时看 9 套主题 + 横竖切换），
却只能靠用户自己注意到顶栏那个不起眼的小控件。

**建议**：首页加一句提示，或在主题页顶部放一行「用顶栏菜单实时切换」。

### 7. favicon 与站点视觉体系不一致 ✅仍存在

**证据**：`packages/docs/public/logo.svg` 为墨色 `#171a18` 底 + 白条 + 钴蓝点；
站点门面为深蓝 `#0e2f74`。

**影响**：favicon 是第一眼认知的唯一入口，目前是墨色，站点是深蓝，两者打架。
且现有图形在 16px 下三根条会粘连。

## P2 — 结构性缺口

### 8. Table 仍是最大空洞 ✅仍存在

**证据**：`docs/component-roadmap.md` 把 Table 列入 Tier 3 并建议
"先做设计规范再开发"；`packages/react/src/` 下**无 `table/` 目录**。

**影响**：数据密集型竖排界面撑不起来——而这恰是最有业务价值的场景。

**建议**：按路线图自己的判断，先出《竖排表格设计规范》（行列语义、表头方向、
滚动与固定），评审通过再开发。不要并入常规组件迭代。

### 9. 缺口清单无法自动同步 ✅仍存在

**证据**：`docs/component-roadmap.md` 是静态 markdown，标注"对标缺口"。

**影响**：组件落地后无机制验证"是否已补齐"，容易出现文档说要做但漏做、
或做了但忘记更新。清单本身也会腐烂。

**建议**：改为机器可读的 `component-status.json`（组件名 / 状态 /
竖排可行性 / 优先级），由脚本生成路线图页面，CI 跑一致性检查。

### 10. 无视觉回归测试 ✅仍存在

**证据**：`vitest.config.ts` 配了 v8 覆盖率，CI 有 `test:coverage`，
但**无任何截图/视觉比对**。

**影响**：竖排组件的视觉回归风险特别高——列缘标记跑到错误的边、
caret 偏移、列间隙被 flex 挤掉，这些**不会让任何单元测试失败**，
只会让界面悄悄变丑。

**建议**：对核心组件（Button / Input / Select / Menu / Tabs）的关键状态
用 Playwright 在 `vertical-lr` 下截图，存 baseline 进仓库，CI 比对。

### 11. API 级检索缺失 ✅仍存在

**证据**：`.dumi/theme/slots/SearchBar` 存在，但无 API 索引；
`ComponentsOverview.tsx` 提供了组件级总览。

**影响**：46 个组件页 / 9 主题 / 6 包，没有 API 索引时只能靠左栏逐项点。
竖排组件的 props 比横排多（如 Button 的 `columnDepth` 这类列相关属性），
查找成本更高。（原文举例的 `verticalMarker` 在代码中不存在，已更正。）

**建议**：自建 `api-index.json` 由组件 JSDoc 生成，优先让 `vertical.*`
相关属性能全局搜到。

### 12. 字体只有 400 字重 ✅仍存在

**证据**：`packages/styles/src/fonts/` 仅 `NotoSansMongolian-400.woff2`。

**影响**：文档站视觉规范要求竖排蒙古文用于 Hero 词标（104–112px）、
组件标本等大字号场景。单字重在超大号下显得单薄，也无法用字重区分层级——
竖排蒙古文的粗细对比是重要可读性手段（尤其低对比度背景）。

**建议**：至少补 500 / 700。若授权或体积受限，考虑可变字体。

### 13. 总览页 Pagination 标本用错了数字 🆕 2026-10-10 新增

**证据**：`packages/docs/src/components/ComponentsOverview.tsx` 的 Pagination 标本写的是
`١ ٢ ٣`（U+0661–U+0663，阿拉伯-印度数字）。

**影响**：蒙古文读者一眼就能看出来，直接损害"蒙文内容可信"这一点；
而交接文档又要求"蒙文一律从这个文件取"，错误会被复制到组件页和设计稿。

**建议**：改为蒙古数字 `᠑ ᠒ ᠓`（U+1811–U+1813）。顺手检查全站蒙文字符是否都在
U+1800–U+18AF 区段内。
